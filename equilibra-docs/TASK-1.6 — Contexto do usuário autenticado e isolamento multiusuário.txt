As TASK-1.1 até TASK-1.5 foram concluídas.

**Sprint 1 — Identidade, Usuários e Autenticação**

Nesta TASK implemente a infraestrutura central para obtenção segura da identidade do usuário autenticado e estabeleça as regras arquiteturais de isolamento multiusuário do Equilibra.

NÃO implemente ainda contas, categorias, transações ou outras entidades financeiras.

# 2. Objetivo

Criar um mecanismo central e seguro através do qual código de aplicação possa descobrir:

**qual usuário está executando esta requisição?**

Exemplo conceitual:

`CurrentUser`

ou:

`AuthenticatedUserProvider`

ou nomenclatura equivalente coerente com a arquitetura.

O mecanismo deverá obter a identidade exclusivamente do contexto autenticado do Spring Security.

---

# 3. Regra arquitetural fundamental

Dados pertencentes ao usuário deverão futuramente ser associados ao usuário autenticado.

O cliente NÃO deverá determinar arbitrariamente o proprietário do recurso.

Evitar contratos como:

`POST /api/expenses?userId=<uuid>`

ou:

{
  "userId": "...",
  "description": "..."
}

quando o `userId` representa o proprietário da operação.

O proprietário deverá ser derivado de:

JWT
↓
Spring Security
↓
SecurityContext
↓
CurrentUser
↓
caso de uso

Documente esta regra como permanente.

---

# 4. Subject do JWT

A TASK-1.5 definiu o UUID do usuário como `sub`.

Reutilize essa decisão.

Não crie um segundo claim como:

`userId`

se `sub` já representa corretamente essa informação.

Evite duplicação.

---

# 5. Principal

Analise a representação efetivamente criada na TASK-1.5.

Se já existe principal tipado contendo o UUID, reutilize-o.

Não crie múltiplas representações concorrentes da mesma identidade sem necessidade.

---

# 6. CurrentUser

Crie uma abstração pequena para obtenção da identidade atual.

Exemplo conceitual:

interface CurrentUser {

    UUID id();

}

ou estrutura equivalente.

Adapte à arquitetura real.

O objetivo é impedir que cada caso de uso precise interpretar diretamente:

- SecurityContextHolder
- Jwt
- claims
- strings

---

# 7. Dependência do Spring Security

Idealmente, regras de negócio futuras não deverão conhecer detalhes de JWT.

Uma feature como:

`AccountService`

deverá poder fazer conceitualmente:

`currentUser.id()`

em vez de:

`SecurityContextHolder.getContext()...`

Isso reduz acoplamento com infraestrutura de segurança.

---

# 8. Implementação

Crie implementação baseada no Spring Security.

Exemplo conceitual:

`SpringSecurityCurrentUser`

Responsabilidades:

1. acessar Authentication atual
2. confirmar autenticação
3. obter principal/subject
4. obter UUID
5. retornar identidade

Não consultar banco sem necessidade.

---

# 9. Ausência de autenticação

Se código que exige usuário autenticado tentar obter CurrentUser sem autenticação válida:

NÃO retornar:

`null`

NÃO retornar UUID fictício.

NÃO utilizar usuário padrão.

Falhe de maneira explícita e segura.

---

# 10. UUID inválido

Se por algum problema a identidade autenticada não puder ser convertida para UUID:

trate como falha de autenticação/estado de segurança.

Não aceite silenciosamente valor inválido.

Isso normalmente não deveria acontecer se JwtDecoder e validações estiverem corretos.

---

# 11. Não confiar em headers alternativos

É PROIBIDO utilizar como identidade:

`X-User-ID`

`User-ID`

`X-Authenticated-User`

ou header customizado enviado pelo cliente.

A única fonte confiável será a autenticação estabelecida pelo Spring Security.

---

# 12. Não confiar em request body

Se futuramente um DTO contiver `userId` por outro motivo legítimo, ele nunca deverá substituir a identidade do proprietário autenticado.

Para recursos privados do usuário:

owner = CurrentUser.id()

e não:

owner = request.userId()

---

# 13. Não confiar em query parameters

O mesmo vale para:

`?userId=...`

O cliente não escolhe o tenant/proprietário dos dados.

---

# 14. Conceito de ownership

Formalize o conceito:

Todo recurso financeiro privado possui um proprietário.

Exemplos futuros:

- AssetAccount
- ExpenseAccount, caso permaneça no modelo
- Category
- Tag
- Expense
- Income
- Transfer
- Attachment
- Report preferences

A propriedade deverá estar vinculada ao usuário autenticado.

NÃO implemente essas entidades nesta TASK.

---

# 15. Estratégia multiusuário

O Equilibra utilizará inicialmente:

**isolamento lógico por usuário no mesmo banco/schema**

e não:

- database per user
- schema per user

Cada registro privado deverá possuir vínculo explícito com seu proprietário quando as entidades forem implementadas.

Documente essa decisão.

---

# 16. Segurança em profundidade

A existência de `CurrentUser` NÃO elimina a necessidade de filtrar consultas pelo proprietário.

Futuramente, evite:

`findById(accountId)`

seguido apenas de validação tardia.

Prefira consultas conceitualmente equivalentes a:

`findByIdAndUserId(accountId, currentUserId)`

ou estratégia igualmente segura.

Isso reduz risco de IDOR/BOLA.

---

# 17. IDOR / BOLA

Documente explicitamente que recursos privados devem ser protegidos contra:

**Insecure Direct Object Reference / Broken Object Level Authorization**

Exemplo futuro:

Usuário A possui conta X.

Usuário B descobre UUID de X.

Usuário B solicita:

`GET /api/accounts/X`

O sistema NÃO poderá retornar a conta.

---

# 18. Estratégia para recurso de outro usuário

Defina convenção para recursos privados.

Quando um recurso não pertence ao usuário autenticado, prefira geralmente:

`404 Not Found`

em vez de revelar:

`403 Forbidden`

quando 403 confirmaria a existência de recurso pertencente a outro usuário.

Documente a decisão.

A aplicação poderá usar 403 em cenários onde existência do recurso já não seja sensível.

---

# 19. Repository pattern futuro

Documente a convenção de que repositories de dados privados devem favorecer métodos ownership-aware.

Exemplos conceituais:

`findByIdAndOwnerId(...)`

`findAllByOwnerId(...)`

`existsByIdAndOwnerId(...)`

Não crie repositories financeiros nesta TASK.

---

# 20. Create

Para criação futura:

owner deverá vir de:

`CurrentUser`

Exemplo conceitual:

request
↓
use case
↓
currentUser.id()
↓
entity.ownerId

Nunca confiar em owner enviado pelo frontend.

---

# 21. Read

Para leitura:

query deverá restringir pelo usuário atual.

Exemplo:

`findAllByOwnerId(currentUser.id())`

---

# 22. Update

Para alteração:

localizar recurso dentro do escopo do usuário.

Não:

1. buscar qualquer recurso por ID
2. aceitar owner do request

---

# 23. Delete

Para exclusão:

aplicar a mesma regra de ownership.

Não permitir exclusão de recurso apenas porque UUID é válido.

---

# 24. Transferências futuras

Transferências serão especialmente sensíveis.

Tanto:

- conta de origem
- conta de destino

deverão pertencer ao usuário autenticado.

Não implementar agora.

Apenas documente a invariável.

---

# 25. Anexos futuros

Anexos deverão herdar o ownership da transação/recurso ao qual pertencem.

Conhecer UUID/nome do arquivo não poderá conceder acesso.

Não implementar armazenamento nesta TASK.

---

# 26. Relatórios futuros

Relatórios deverão consultar somente dados pertencentes ao CurrentUser.

Filtros de contas deverão ser validados dentro do mesmo ownership.

---

# 27. Auditoria futura

A auditoria deverá utilizar identidade autenticada para atribuir ações.

Não aceite `performedByUserId` vindo do frontend.

Não implementar auditoria funcional nesta TASK.

# 28. Endpoint `/me`

Implemente um endpoint autenticado mínimo para representar o usuário atual.

Sugestão:

`GET /api/users/me`

ou rota coerente com a convenção existente.

Objetivos:

- provar o contexto autenticado
- fornecer identidade básica ao frontend futuramente
- validar JWT → SecurityContext → CurrentUser

---

# 29. Response de `/me`

Retorne somente informações seguras e úteis.

Sugestão:

{
  "id": "<uuid>",
  "email": "user@example.com"
}

Pode incluir:

- createdAt

somente se houver benefício claro.

Não retornar:

- password
- passwordHash
- informações de segurança
- claims internos desnecessários

---

# 30. Origem do ID em `/me`

O ID deverá vir da identidade autenticada.

Não aceite:

`GET /api/users/me?userId=...`

---

# 31. Email em `/me`

Como email não precisa estar no JWT, o endpoint poderá consultar UserRepository utilizando:

`CurrentUser.id()`

para carregar informações do perfil.

Essa consulta é apropriada porque `/me` precisa de dados atuais do usuário.

Isso NÃO significa que toda requisição autenticada deve consultar o banco.

---

# 32. Usuário removido/inconsistente

Caso o JWT seja criptograficamente válido mas o usuário correspondente não exista mais no banco ao chamar `/me`:

trate de forma segura.

Não retorne 500 por simples ausência do usuário.

Escolha comportamento coerente e documente.

---

# 33. Usuário desativado após emissão

A TASK-1.5 provavelmente adotou access token curto sem consulta ao banco em toda requisição.

Mantenha essa decisão salvo problema real.

Portanto, um token emitido antes da desativação poderá permanecer válido até expirar.

Porém `/me`, ao consultar usuário atual, poderá detectar `active=false`.

Defina comportamento consistente.

Não implemente blacklist.

---

# 34. Segurança do `/me`

`GET /api/users/me`

deve exigir autenticação.

Sem token:

`401`

Token inválido:

`401`

Token válido:

`200`
