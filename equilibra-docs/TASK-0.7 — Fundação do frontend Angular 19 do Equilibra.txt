# TASK-0.7 — Fundação do frontend Angular 19 do Equilibra

Leia integralmente antes de realizar alterações:

- `CLAUDE.md`
- `docs/architecture.md`
- `docs/api-guidelines.md`
- ADRs existentes
- README

Analise o estado atual do diretório `/frontend`.

Esta TASK deve estabelecer a fundação arquitetural e visual do frontend.

NÃO implemente funcionalidades financeiras.

---

# 1. Objetivo

Criar ou consolidar o frontend do Equilibra utilizando:

- Angular 19
- TypeScript
- Angular Material
- SCSS
- Standalone Components
- Angular Router
- Signals quando apropriado
- Reactive Forms para formulários futuros

O resultado deverá ser uma aplicação:

- moderna
- limpa
- responsiva
- acessível
- preparada para desktop
- preparada para tablet
- preparada para smartphone

Não implementar ainda:

- login funcional
- cadastro de usuário
- Dashboard funcional
- contas
- categorias
- tags
- transações
- relatórios

---

# 2. Verificar projeto existente

Antes de criar qualquer coisa:

1. Analise o `package.json`.
2. Confirme a versão efetivamente instalada do Angular.
3. Analise a estrutura existente.
4. Analise configuração TypeScript.
5. Analise configuração de testes.
6. Analise estilos existentes.
7. Verifique se Angular Material já está instalado.
8. Verifique se SSR foi configurado.
9. Verifique configuração de linting.
10. Verifique scripts existentes.

Não recrie o projeto Angular se ele já estiver corretamente inicializado.

Não faça upgrade/downgrade desnecessário.

Preserve Angular 19 conforme definido pelo projeto.

---

# 3. Arquitetura frontend

Organize o frontend conceitualmente em:

src/app/
├── core/
├── shared/
├── layout/
└── features/

## core

Deverá conter infraestrutura global da aplicação quando necessária, como futuramente:

- configuração HTTP
- interceptors
- guards
- autenticação
- serviços singleton globais

Não crie implementações fictícias nesta TASK.

## shared

Componentes, diretivas, pipes e utilitários verdadeiramente reutilizáveis.

Não transforme `shared` em depósito genérico.

## layout

Responsável pela estrutura visual principal:

- application shell
- header/toolbar
- sidebar/navigation
- área de conteúdo

## features

Funcionalidades de negócio.

Módulos futuros:

- auth
- dashboard
- accounts
- categories
- tags
- transactions
- reports

Não crie estruturas vazias apenas para representar funcionalidades futuras.

---

# 4. Standalone Components

Utilize Standalone Components.

Não introduza NgModules para funcionalidades novas sem necessidade técnica concreta.

Utilize APIs modernas do Angular 19 quando apropriado.

Não migre código existente funcional apenas por preferência estilística sem necessidade.

---

# 5. Application Shell

Implemente um shell visual base contendo:

- toolbar/header
- sidebar/drawer
- área principal para router outlet

Estrutura conceitual:

+--------------------------------------------------+
| Equilibra                              usuário   |
+--------------+-----------------------------------+
|              |                                   |
| Navegação    |          Conteúdo                 |
|              |                                   |
|              |                                   |
+--------------+-----------------------------------+

No desktop:

- sidebar lateral visível
- conteúdo ao lado

No mobile:

- sidebar deverá funcionar como drawer
- aberta através de botão/menu
- conteúdo ocupa largura disponível

Não utilize largura fixa que prejudique telas pequenas.

---

# 6. Navegação

Prepare visualmente o menu futuro:

- Dashboard

- Cadastros
  - Contas
  - Categorias
  - Tags

- Transações
  - Despesas
  - Receitas
  - Transferências

- Relatórios

Nesta TASK esses itens NÃO precisam direcionar para funcionalidades reais.

Evite criar páginas completas fictícias.

Quando necessário para validar o router, utilize somente placeholders mínimos claramente identificados como temporários.

Não implemente regras financeiras.

---

# 7. Menu Transações

"Transações" deverá funcionar visualmente como grupo expansível/colapsável contendo:

- Despesas
- Receitas
- Transferências

"Cadastros" também poderá ser agrupado contendo:

- Contas
- Categorias
- Tags

Escolha uma solução consistente utilizando Angular Material.

Garanta navegação adequada por teclado.

---

# 8. Header

O header deverá possuir inicialmente:

- identidade Equilibra
- botão para menu em telas pequenas
- espaço reservado para informações do usuário autenticado

Como autenticação ainda não existe, NÃO crie usuário fake.

Não exiba nomes fictícios como:

"João Silva"

Se for necessário representar a área futura, utilize somente estrutura neutra.

Não implemente logout ainda.

---

# 9. Identidade visual

Crie uma identidade visual inicial consistente para o Equilibra.

Objetivos visuais:

- confiança
- organização
- equilíbrio
- simplicidade
- finanças pessoais

Utilize como direção principal tons de:

- teal
- verde moderado
- superfícies neutras
- cinzas suaves

Evite:

- verde neon
- excesso de gradientes
- sombras exageradas
- excesso de cores
- aparência de dashboard corporativo antigo

A interface deve parecer uma aplicação financeira moderna.

---

# 10. Design tokens

Evite espalhar valores visuais arbitrários pelo SCSS.

Centralize quando apropriado:

- espaçamento
- border radius
- tamanhos principais
- superfícies
- cores semânticas

Utilize o sistema de theming do Angular Material sempre que possível.

Não construa um design system excessivamente complexo.

---

# 11. Tema

Configure um tema claro consistente do Angular Material.

Prepare a estrutura para que futuramente seja possível implementar dark mode sem reescrever todos os componentes.

NÃO implemente dark mode nesta TASK.

Não crie botão de troca de tema ainda.

---

# 12. Tipografia

Utilize uma hierarquia tipográfica consistente.

Defina estilos adequados para:

- título da página
- subtítulo
- headings
- corpo
- labels
- textos auxiliares

Evite tamanhos excessivamente pequenos em mobile.

Não dependa de fontes externas sem necessidade.

Se utilizar uma fonte externa, justifique e avalie impacto de carregamento e privacidade.

Prefira inicialmente fontes do sistema quando possível.

---

# 13. Responsividade

Considere pelo menos:

## Mobile

aproximadamente abaixo de 600px

## Tablet

aproximadamente 600px–959px

## Desktop

aproximadamente 960px ou superior

Não trate esses valores como regra absoluta caso Angular Material forneça abordagem melhor.

A interface deverá funcionar adequadamente desde aproximadamente 360px de largura.

Não deverá existir scroll horizontal causado pelo layout principal.

---

# 14. Mobile first

Desenvolva estilos considerando telas pequenas primeiro quando apropriado.

Elementos interativos devem possuir área adequada para toque.

Não dependa exclusivamente de hover.

---

# 15. Área principal

A área de conteúdo deverá possuir:

- largura responsiva
- padding consistente
- espaço adequado entre seções

Em monitores grandes, evite que conteúdos de formulário fiquem exageradamente largos quando isso prejudicar legibilidade.

Não imponha limite que prejudique dashboards futuros.

---

# 16. Page container

Se houver benefício concreto, crie um componente estrutural reutilizável para páginas.

Exemplo conceitual:

PageContainer

com suporte a:

- título
- subtítulo opcional
- actions
- conteúdo

Não crie abstrações excessivas.

Esse componente poderá ser utilizado futuramente em:

- Contas
- Categorias
- Transações
- Relatórios

---

# 17. Empty State

Se fizer sentido nesta TASK, crie um componente simples reutilizável de estado vazio.

Exemplo futuro:

"Nenhuma transação encontrada."

Porém, não crie dezenas de componentes compartilhados antecipadamente.

---

# 18. Loading

Defina uma estratégia visual para carregamento futuro utilizando Angular Material.

Não implemente um sistema global complexo de loading.

Pode ser documentada a utilização de:

- progress spinner
- progress bar
- skeleton futuramente quando necessário

---

# 19. Feedback

Defina como padrão futuro:

- snackbar para feedback transitório
- dialog para confirmações relevantes
- erros de formulário próximos ao campo

Não implemente serviços globais complexos sem uso real.

---

# 20. Acessibilidade

A interface deverá considerar:

- HTML semântico
- navegação por teclado
- foco visível
- labels apropriados
- ARIA somente quando necessário
- contraste adequado
- botões com nomes acessíveis
- ícones com descrição quando comunicarem informação

Não utilizar somente cor para indicar significado financeiro.

---

# 21. Ícones

Utilize Angular Material Icons ou solução já existente no projeto.

Mantenha consistência.

Não instale múltiplas bibliotecas de ícones.

---

# 22. Rotas

Configure uma estrutura limpa de roteamento.

Prepare o sistema para lazy loading das features futuras.

Não carregue todas as funcionalidades antecipadamente.

O shell deverá conter o `router-outlet` apropriado.

Nesta TASK pode existir uma rota inicial temporária apenas para demonstrar o funcionamento do shell.

Essa rota será substituída pelo Dashboard real futuramente.

Não crie gráficos fictícios.

Não crie dados financeiros fake.

# 24. Configuração de ambientes

Analise a estratégia Angular existente para configuração de ambiente.

Prepare uma forma limpa de configurar a URL base da API.

Não espalhe:

`http://localhost:8080`

pelo código.

Deve existir um ponto central para configuração futura da API.

A integração efetiva com o backend será realizada na TASK-0.8.

---

# 25. HTTP

Prepare o Angular para utilizar `HttpClient` através das APIs modernas de providers.

Não crie serviços HTTP fictícios para:

- Account
- Transaction
- Category

Apenas prepare a infraestrutura mínima necessária.

---

# 26. Interceptors

Não implemente JWT interceptor nesta TASK.

Autenticação ainda não existe.

Apenas mantenha arquitetura preparada para interceptors futuros.

O request ID será tratado na TASK-0.8 se decidirmos propagá-lo a partir do frontend.

---

# 27. Formulários

Reactive Forms será o padrão para formulários de negócio.

Não crie formulários financeiros nesta TASK.

Documente a decisão arquitetural.

---

# 28. Estado

Não instale NgRx, Akita ou outra biblioteca global de estado nesta TASK.

Utilize inicialmente recursos nativos do Angular:

- Signals
- services
- RxJS quando apropriado

Uma biblioteca de estado somente deverá ser adicionada se a complexidade futura justificar.

---

# 29. RxJS e Signals

Use:

Signals para estado local/síncrono quando apropriado.

RxJS para fluxos assíncronos e HTTP quando apropriado.

Não converta tudo para Signals ou tudo para Observables de forma dogmática.

---

# 30. SCSS

Organize os estilos globais de maneira simples.

Evite:

- `!important` indiscriminado
- seletores profundamente aninhados
- CSS duplicado
- estilos globais que vazem para features

Utilize estilos de componentes quando apropriado.

---

# 31. Qualidade TypeScript

Mantenha TypeScript strict quando já configurado ou quando puder ser ativado sem quebrar injustificadamente a base.

Evite:

`any`

quando um tipo adequado puder ser definido.

Não utilize casts apenas para silenciar erros sem compreender a causa.

Não adicione múltiplas ferramentas concorrentes.

Não faça alterações massivas de formatação em arquivos não relacionados.
