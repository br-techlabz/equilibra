# TASK-6.5 — ALERTAS DE LIMITES DE GASTOS

PROJETO: EQUILIBRA
SPRINT: 6 — PLANEJAMENTO FINANCEIRO

CONTEXTO

TASK-6.0 — Arquitetura do Planejamento Financeiro concluída.
TASK-6.1 — Backend de Orçamentos por Categoria concluído.

TASK-6.3 — Backend de Planejado versus Realizado concluído.
TASK-6.4 — Dashboard de Acompanhamento concluído.

OBJETIVO

Implementar alertas in-app de consumo de orçamento,
identificando categorias que:

- estão dentro do limite;
- estão próximas do limite;
- atingiram o limite;
- ultrapassaram o limite.

Os alertas devem ser derivados dos dados reais
de orçamento e consumo, sem alterar o ledger.

Não implementar notificações externas.

IMPORTANTE

O ADR da TASK-6.0 é a fonte de verdade.

Os limiares, nomes dos estados, contratos REST
e decisões de persistência devem seguir o ADR.

Os exemplos deste prompt não autorizam criar
regras divergentes das já aprovadas.

==================================================
6. LIMIARES
==================================================

Usar os limiares aprovados.

Exemplo APENAS ILUSTRATIVO:

ON_TRACK:
consumo menor que 80%.

WARNING:
consumo de 80% até menos de 100%.

LIMIT_REACHED:
consumo exatamente igual a 100%.

EXCEEDED:
consumo acima de 100%.

Não adotar automaticamente esses valores.

==================================================
7. COMPARAÇÃO MONETÁRIA
==================================================

A classificação deve evitar erros
decorrentes de arredondamento de percentual.

Se o ADR permitir, utilizar comparações
com BigDecimal e valores monetários exatos.

Exemplo:

planned=1000.00
actual=1000.00

Deve representar exatamente o limite.

Não classificar como excedido por erro
de representação numérica.

==================================================
8. ORÇAMENTO ZERO
==================================================

Seguir a semântica aprovada.

Casos:

planned=0;
actual=0.

planned=0;
actual>0.

Não dividir por zero.

Não apresentar NaN ou Infinity.

Não inventar status que contradiga o ADR.

==================================================
9. ORÇAMENTO EXCEDIDO
==================================================

Exemplo:

planned=1000.00
actual=1150.00

remaining=-150.00
percentage=115%.

Exibir:

"Limite excedido"

Não limitar o percentual textual a 100%.

Não transformar restante negativo em zero.

==================================================
10. ORÇAMENTO ATINGIDO
==================================================

Exemplo:

planned=1000.00
actual=1000.00

A apresentação deve respeitar a regra aprovada
para exatamente 100%.

Não confundir atingido com excedido.

==================================================
11. ORÇAMENTO PRÓXIMO DO LIMITE
==================================================

Quando o orçamento entrar na faixa de atenção
aprovada no ADR, apresentar aviso claro.

Exemplo de texto:

"Você está próximo do limite planejado
para esta categoria."

Não apresentar alertas alarmistas.

==================================================
12. CANCELAMENTO DE DESPESA
==================================================

Se uma despesa for cancelada:

o valor realizado diminui conforme ledger.

O alerta deve refletir automaticamente
o novo estado na próxima consulta.

Não manter alerta antigo como verdadeiro
se a condição deixou de existir.

==================================================
13. EDIÇÃO DE ORÇAMENTO
==================================================

Se plannedAmount mudar:

recalcular classificação a partir dos dados
atualizados do backend.

Exemplo:

planned=500
actual=450.

Após editar planned=1000:

o alerta deve refletir o novo limite.

Não manter estado obsoleto no frontend.

==================================================
14. COMPETÊNCIA
==================================================

Alertas devem corresponder à competência
selecionada.

Não misturar orçamentos de meses diferentes.

Definir no ADR se alertas históricos
aparecem somente como indicadores históricos,
sem notificação ativa.

==================================================
15. CATEGORIAS INATIVAS
==================================================

Orçamentos históricos com categorias inativas
devem permanecer visíveis conforme ADR.

Alertas derivados devem seguir o comportamento
documentado para consultas históricas.

Não ocultar categoria apenas por estar inativa.

==================================================
16. CATEGORIA BOTH
==================================================

Uma categoria BOTH pode ter orçamento de despesa.

Somente despesas válidas contribuem
para o consumo.

Receitas não reduzem o realizado.

==================================================
17. TRANSFERÊNCIAS
==================================================

Transferências não devem gerar alertas
de consumo de orçamento.

Não somar transferências como despesas.

==================================================
18. DESPESAS NÃO ORÇADAS
==================================================

Despesas em categorias sem orçamento
não devem gerar alerta de estouro de um
orçamento inexistente.

Se existir indicador de despesas não orçadas,
tratá-lo separadamente.
