# 4. Entidade User

Crie uma entidade representando o usuário do Equilibra.

Utilize nome Java coerente com o projeto.

Exemplo:

`User`

Caso exista conflito técnico ou semântico relevante, utilize nome alternativo e documente a decisão.

---

# 5. Campos

A entidade deverá possuir inicialmente:

- id
- email
- passwordHash
- active
- createdAt
- updatedAt

Não adicione campos pessoais sem requisito.

NÃO adicionar nesta TASK:

- nome
- CPF
- telefone
- endereço
- foto
- data de nascimento
- gênero
- preferências financeiras

O princípio é armazenar somente o necessário.

---

# 6. ID

Utilize a estratégia de identificadores definida na Sprint 0.

Preferencialmente:

UUID

caso essa tenha sido a decisão arquitetural aprovada.

O ID deverá ser gerado de maneira consistente.

Não utilize IDs sequenciais se isso contrariar a arquitetura existente.

---

# 7. Email

O email será utilizado como login.

Portanto:

- obrigatório
- não pode ser vazio
- deve possuir tamanho máximo definido
- deverá possuir constraint UNIQUE no banco
- deverá possuir índice adequado

A unicidade deverá ser garantida pelo banco, não apenas pelo Java.

---

# 8. Normalização de email

Defina e documente uma política consistente.

Antes da persistência futura, o sistema deverá considerar o email normalizado.

No mínimo:

- remover espaços externos
- tratar casing de maneira consistente

Exemplo conceitual:

`usuario@exemplo.com`

e

`USUARIO@EXEMPLO.COM`

não deverão resultar em duas contas independentes.

Como o fluxo de cadastro será implementado posteriormente, nesta TASK prepare a modelagem para garantir essa propriedade.

Escolha uma estratégia compatível com MySQL e documente-a.

Não implemente regras complexas específicas de provedores de email.

NÃO:

- remover pontos do Gmail
- interpretar aliases `+`
- alterar semanticamente o endereço

---

# 9. Password Hash

A entidade deverá armazenar:

`passwordHash`

NUNCA:

`password`

em texto puro.

Nesta TASK não é necessário implementar o algoritmo de hash.

Isso será tratado na TASK-1.2.

Entretanto, o banco deverá possuir coluna adequada para armazenar hashes produzidos pela estratégia futura.

Não registre passwordHash em:

- logs
- `toString`
- exceptions
- respostas

---

# 10. Active

Adicione:

`active`

booleano.

Valor inicial:

`true`

O campo permitirá futuramente desativar contas sem necessariamente excluir imediatamente seus registros.

Não implemente fluxo de desativação nesta TASK.

---

# 11. Timestamps

Utilize a estratégia definida na arquitetura.

Campos:

`createdAt`
`updatedAt`

Preferencialmente representados no Java através de:

`Instant`

quando consistente com a Sprint 0.

Armazene os valores de maneira coerente com UTC.

Não dependa do timezone local da máquina.

---

# 12. Auditoria automática de timestamps

Escolha uma solução simples e compatível com a arquitetura existente.

Pode utilizar mecanismos JPA/Hibernate apropriados ou callbacks quando necessário.

Evite adicionar framework de auditoria apenas para dois timestamps.

Garanta que:

- `createdAt` seja definido na criação
- `updatedAt` seja atualizado em alterações

Não implemente o módulo de auditoria funcional nesta TASK.

---

# 13. Nome da tabela

Evite nomes que possam conflitar com palavras reservadas.

Prefira:

`users`

ou outro nome consistente com a convenção existente.

Verifique compatibilidade com MySQL.

---

# 14. Migration Flyway

Crie uma NOVA migration.

Não altere migrations aplicadas na Sprint 0.

Utilize a próxima versão disponível.

Exemplo conceitual:

`V2__create_users.sql`

mas determine a versão real observando as migrations existentes.

A migration deverá criar a tabela de usuários.

---

# 15. Schema

A tabela deverá refletir explicitamente:

- primary key
- email obrigatório
- unicidade do email
- password_hash obrigatório
- active obrigatório
- created_at obrigatório
- updated_at obrigatório

Escolha tipos MySQL apropriados.

---

# 16. UUID no MySQL

Utilize a representação de UUID coerente com a decisão arquitetural existente.

Não escolha arbitrariamente entre:

- CHAR(36)
- BINARY(16)

sem considerar a configuração JPA/Hibernate.

Documente a escolha.

Priorize consistência e manutenção.

Não faça otimização prematura apenas para economizar alguns bytes.

---

# 17. Índices

Analise os acessos futuros.

Login fará consulta frequente por email.

Garanta índice eficiente.

Evite criar índices redundantes se a constraint UNIQUE já fornecer índice adequado no MySQL.

---

# 18. Repository

Crie repository para persistência do usuário utilizando Spring Data JPA.

Ele deverá fornecer somente operações necessárias nesta fase/futuro imediato.

Prepare consulta por email normalizado.

Exemplo conceitual:

`findByEmail(...)`

ou equivalente consistente com a estratégia adotada.

Evite criar métodos especulativos.

---

# 19. Exists

Como o cadastro futuro precisará verificar email existente, avalie fornecer:

`existsByEmail(...)`

se isso for coerente.

Entretanto, lembre-se:

a constraint UNIQUE no banco continua sendo a garantia definitiva contra race conditions.

---

A entidade `User` NÃO deverá ser exposta diretamente por API.

Embora não exista controller nesta TASK, preserve essa regra.

Não adicione serialização JSON à entidade sem necessidade.

# 26. Testes de persistência

Crie testes utilizando MySQL via Testcontainers, reutilizando a infraestrutura da Sprint 0.

Não utilize H2.

Cubra pelo menos:

### Persistência

Criar usuário válido e recuperar pelo ID.

### Busca por email

Persistir usuário e recuperar através do email normalizado.

### Unicidade

Tentar persistir dois usuários com o mesmo email normalizado deve resultar em violação da constraint.

### Active

Novo usuário deve possuir estado coerente com o modelo definido.

### Timestamps

Verifique criação de:

- createdAt
- updatedAt

quando apropriado.
