# TASK-1.7 — Frontend Angular: cadastro de usuário

As TASK-1.1 até TASK-1.6 foram concluídas.

Estamos na:

**Sprint 1 — Identidade, Usuários e Autenticação**

Nesta TASK implemente a primeira funcionalidade real de identidade no frontend:

**Criação de conta**

Fluxo:

Usuário
→ página de cadastro
→ formulário Angular
→ POST /api/auth/register
→ conta criada
→ feedback
→ redirecionamento para login

NÃO implemente autenticação JWT no frontend nesta TASK.

# 11. Email — validação frontend

Valide coerentemente com o backend:

- obrigatório
- formato
- tamanho máximo

Não crie regras frontend mais restritivas sem necessidade.

O backend continua sendo autoridade final.

---

# 12. Senha — política

Utilize a política REAL definida na TASK-1.2.

Não invente valores.

Se a política atual for, por exemplo:

- mínimo 8
- máximo 128

o frontend deverá refletir exatamente isso.

Não exigir:

- maiúscula
- símbolo
- número

se o backend não exige.

---

# 13. Confirmação

`password` e `confirmPassword` deverão coincidir.

A validação deve ocorrer no frontend.

Se diferentes:

- impedir submit
- apresentar mensagem acessível

Não enviar confirmação ao backend.

---

# 14. Espaços da senha

NÃO utilizar `trim()` na senha.

NÃO modificar a senha.

Preserve exatamente o valor digitado.

Isso deve ser consistente com TASK-1.2.

---

# 15. Email

Pode aplicar a normalização visual apropriada quando coerente, mas o backend continua responsável pela normalização definitiva.

Evite alterar o email de maneira surpreendente enquanto o usuário digita.

---

# 16. Mostrar/ocultar senha

- nome acessível
- `aria-label` adequado

Não depender apenas do ícone.

# 17. Indicador de força

# 24. Erro 400

Quando backend retornar validação:

- associe erros de campo aos campos correspondentes quando possível
- apresente mensagem adequada

Não mostrar JSON bruto.

Não mostrar stack trace.

---

# 25. Erro 409

Email já cadastrado:

apresente mensagem clara, por exemplo:

"Já existe uma conta cadastrada com este e-mail."

Utilize o Problem Details real quando possível.

Não trate todo 409 como email duplicado se a API puder ter outros conflitos.

---

# 26. Enumeração

Cadastro necessariamente informa que um email já existe através do 409 definido no backend.

Mantenha comportamento consistente com a API.

Não revele qualquer informação adicional sobre a conta.

---

# 27. Erro de rede

Se backend estiver indisponível:

apresente mensagem amigável.

Exemplo:

"Não foi possível conectar ao serviço. Tente novamente."

Não mostrar:

- URL interna
- status 0
- stack trace

---

# 28. Erro 500

Apresente mensagem genérica.

Exemplo:

"Não foi possível criar sua conta. Tente novamente."

Preserve request ID internamente quando infraestrutura existente permitir diagnóstico.

---

# 29. Feedback de sucesso

Após `201 Created`:

apresente confirmação clara.

Exemplo:

"Conta criada com sucesso."

Depois encaminhe o usuário para:

`/login`

Não autenticar automaticamente.

---

# 30. Redirecionamento

Evite delay artificial longo.

Pode:

1. mostrar snackbar
2. navegar imediatamente para login

ou estratégia equivalente consistente.

Não utilizar `setTimeout` desnecessariamente.

---

Essa página deve indicar de forma limpa que o login será implementado na próxima TASK.

NÃO criar formulário de login funcional nesta TASK.

NÃO consumir `/api/auth/login`.

Após erro retornado pelo backend, mantenha navegação previsível.

Não implemente solução excessivamente complexa.
