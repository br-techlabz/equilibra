# TASK-1.5 — JWT e autorização stateless

As TASK-1.1 até TASK-1.4 foram concluídas.

Estamos na:

**Sprint 1 — Identidade, Usuários e Autenticação**

Nesta TASK transforme a autenticação de credenciais já existente em autenticação HTTP stateless utilizando access token JWT.

Fluxo alvo:

email + senha
↓
autenticação
↓
identidade autenticada
↓
access token JWT assinado
↓
cliente envia Authorization: Bearer <token>
↓
Spring Security valida token
↓
SecurityContext
↓
endpoint protegido

NÃO implemente refresh token nesta TASK.

# 2. Objetivo

Implementar:

- geração de access token JWT
- assinatura criptográfica
- expiração
- validação do token
- autenticação Bearer
- criação do SecurityContext
- proteção de endpoints
- respostas 401/403 consistentes
- integração com OpenAPI

A API deverá permanecer stateless.

---

# 3. Utilizar Spring Security

Utilize recursos oficiais do Spring Security para processamento JWT sempre que possível.

Prefira mecanismos modernos suportados pela versão instalada, como:

- OAuth2 Resource Server
- JwtEncoder
- JwtDecoder

quando apropriado.

Evite implementar manualmente:

- parsing JWT
- validação de assinatura
- Base64
- comparação de assinatura
- filtro criptográfico próprio

Não adicione biblioteca JWT externa se Spring Security já atender adequadamente ao requisito.

---

# 4. Dependências

Verifique primeiro as dependências existentes.

Caso necessário, adicione dependência oficial do ecossistema Spring para Resource Server/JWT.

Evite bibliotecas concorrentes como várias implementações JWT simultaneamente.

Não sobrescreva versões gerenciadas pelo Spring Boot sem necessidade.

---

# 5. Algoritmo de assinatura

Avalie a estratégia de assinatura mais adequada para esta aplicação.

Prefira assinatura assimétrica quando ela puder ser configurada de maneira simples, segura e compatível com a infraestrutura atual.

Exemplos possíveis:

- RSA
- EC

Caso escolha assinatura simétrica, documente claramente:

- motivo
- requisitos de tamanho/entropia do secret
- estratégia de configuração

NUNCA:

- hardcode chave
- versionar private key
- versionar secret real
- utilizar senha humana como JWT secret

Documente a decisão tomada.

---

# 6. Chaves

Se utilizar assinatura assimétrica:

private key:
- usada para assinatura
- nunca versionada
- nunca enviada ao frontend

public key:
- usada para validação

Configure através de mecanismo seguro e apropriado ao ambiente.

Para desenvolvimento, forneça instruções de geração/configuração.

Não coloque chave privada real no Git.

Se forem necessários arquivos de exemplo, eles NÃO podem representar segredo utilizável em produção.

# 7. Configuração

Centralize configurações JWT.

Exemplo conceitual:

`JwtProperties`

Propriedades possíveis:

- issuer
- access-token-ttl
- chave/configuração criptográfica

Não espalhe strings e durações pelo código.

Utilize configuração externa.

---

# 8. Issuer

Defina um issuer consistente.

Exemplo conceitual:

`equilibra-api`

Não invente domínio público inexistente.

O decoder deverá validar issuer quando tecnicamente apropriado.

---

# 9. Expiração

Access token deve possuir duração limitada.

Adote inicialmente duração curta e razoável.

Sugestão:

15 minutos

ou outro valor justificado.

A duração deverá ser configurável.

Não crie token sem expiração.

---

# 10. Claims mínimos

Inclua somente claims necessários.

Considere:

- `iss`
- `sub`
- `iat`
- `exp`
- `jti`

Para `sub`, prefira identificador imutável do usuário, como UUID.

Não utilize email como identidade principal do token se o UUID estiver disponível.

---

# 11. Email no JWT

Evite incluir email se ele não for necessário para autorização.

O token deve minimizar dados pessoais.

Se o frontend futuramente precisar do email, ele poderá obtê-lo através de endpoint autenticado apropriado.

Não transforme JWT em perfil de usuário.

---

# 12. Claims proibidos

NUNCA colocar no JWT:

- password
- passwordHash
- secrets
- dados bancários
- saldos
- transações
- anexos
- informações sensíveis desnecessárias

---

# 13. Roles/authorities

O Equilibra ainda não possui requisito de múltiplos papéis administrativos.

Não invente:

- ROLE_ADMIN
- ROLE_PREMIUM
- ROLE_MANAGER

se eles não existem no produto.

Todo usuário autenticado pode inicialmente possuir a autoridade mínima necessária, ou a autorização pode depender apenas de autenticação.

Documente a escolha.

---

# 14. JTI

Avalie incluir `jti` único no token.

Pode utilizar UUID.

Não implemente blacklist/revocation store nesta TASK.

O `jti` prepara a arquitetura para necessidades futuras sem obrigar armazenamento server-side.

---

# 15. Geração do token

Crie componente responsável exclusivamente por geração de tokens.

Exemplo conceitual:

`JwtTokenService`

Responsabilidades:

- receber identidade autenticada
- criar claims
- definir timestamps
- assinar token

Não colocar geração JWT no controller.

---

# 16. Clock

Evite chamadas dispersas a `Instant.now()` quando isso prejudicar testabilidade.

Avalie injetar:

`Clock`

ou abstração equivalente.

Isso permite testar:

- issuedAt
- expiration

de maneira determinística.

Não crie abstração exagerada.

---

# 17. Login response

Evolua a resposta de:

`POST /api/auth/login`

para retornar access token.

Exemplo conceitual:

{
  "accessToken": "...",
  "tokenType": "Bearer",
  "expiresIn": 900
}

Adapte naming à convenção JSON existente.

Não retornar:

- password
- passwordHash
- private key
- refresh token fictício

---

# 18. Informações adicionais no login

Mantenha a resposta mínima.

Se já houver `id` e `email` da TASK-1.4, avalie se ainda são necessários.

Prefira evitar duplicação de identidade quando futuramente teremos endpoint `/me`.

Documente a decisão.

---

# 19. Access token apenas

Nesta TASK existe apenas:

`accessToken`

NÃO criar:

`refreshToken`

NÃO criar token vazio ou placeholder.

---

# 20. Bearer Authentication

Requisições autenticadas deverão utilizar:

`Authorization: Bearer <access-token>`

Utilize suporte padrão Spring Security.

Não crie header proprietário.

---

# 21. Validação

O backend deverá validar pelo menos:

- estrutura JWT
- assinatura
- issuer
- expiration
- claims obrigatórios relevantes

Token inválido NÃO autentica.

---

# 22. Token expirado

Token expirado:

→ `401 Unauthorized`

Não retornar stack trace.

Não retornar detalhes criptográficos.

Mensagem poderá indicar autenticação inválida/expirada sem revelar internals.

---

# 23. Token adulterado

Qualquer modificação no payload sem nova assinatura válida:

→ `401 Unauthorized`

Crie teste explícito.

---

# 24. Token malformado

Valor Bearer que não seja JWT válido:

→ `401 Unauthorized`

Sem:

- stack trace
- Base64 errors
- detalhes internos

---

# 25. Token ausente

Endpoint protegido sem token:

→ `401 Unauthorized`

Endpoint público continua funcionando normalmente.

---

# 26. SecurityContext

Após validação, o Spring Security deverá possuir identidade autenticada disponível no:

`SecurityContext`

A identidade deverá permitir obter no mínimo:

`userId`

Isso será fundamental na TASK-1.6.

---

# 27. Principal

Defina representação clara do principal autenticado.

Prefira identidade imutável.

Exemplo conceitual:

`AuthenticatedPrincipal`

contendo:

- userId

e somente outros campos realmente necessários.

Não coloque entidade JPA completa no SecurityContext sem necessidade.

---

# 28. Banco por request

Evite consultar `users` em TODA requisição apenas para reconstruir uma identidade que já está validamente representada no JWT, salvo se houver requisito de segurança que justifique.

Entretanto, considere a implicação do campo:

`active`

Um usuário desativado após emissão do token poderá continuar autenticado até o token expirar.

Com access token curto, esse trade-off pode ser aceitável para o MVP.

Documente explicitamente essa decisão.

Não implemente blacklist nesta TASK.

---

# 29. Endpoints públicos

Mantenha públicos somente os endpoints necessários.

No mínimo:

- `POST /api/auth/register`
- `POST /api/auth/login`

Além dos endpoints técnicos explicitamente aprovados na Sprint 0, como health/OpenAPI conforme configuração existente.

Não liberar:

`/api/**`

indiscriminadamente.

---

# 30. Endpoints protegidos

Todos os endpoints de negócio futuros deverão ser autenticados por padrão.

Adote estratégia:

**deny/protect by default**

e permita explicitamente apenas endpoints públicos.

Isso reduz risco de novos endpoints nascerem públicos acidentalmente.

---

# 31. Endpoint técnico protegido para teste

Não crie endpoint permanente como:

`/api/test/protected`

somente para testar segurança.

Utilize controller restrito aos testes quando necessário.

---

# 32. 401 vs 403

Defina corretamente:

### 401 Unauthorized

Usuário não autenticado ou credencial/token inválido.

### 403 Forbidden

Usuário autenticado, mas sem autorização para determinada operação.

Não utilizar 403 para token ausente.

---

# 33. Problem Details

Integre 401 e 403 ao padrão de erros existente quando tecnicamente compatível com Spring Security.

IMPORTANTE:

Erros produzidos dentro do filter chain podem não passar pelo `@RestControllerAdvice`.

Implemente mecanismos apropriados, como:

- AuthenticationEntryPoint
- AccessDeniedHandler

quando necessário.

As respostas devem ser coerentes com Problem Details.

---

# 34. Request ID

401 e 403 produzidos pela camada de segurança também deverão preservar:

`X-Request-ID`

e, quando a arquitetura atual fizer isso, incluir request ID no Problem Details.

Garanta ordem correta dos filtros.

---

# 35. Ordem dos filtros

Analise:

- RequestIdFilter

- Resource Server

Garanta que request ID esteja disponível durante tratamento de erros de autenticação.

Não registre filtros duplicados acidentalmente.
