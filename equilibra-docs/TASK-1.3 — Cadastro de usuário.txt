# 2. Objetivo

Permitir que uma pessoa crie uma conta no Equilibra utilizando:

- email
- senha

Endpoint:

`POST /api/auth/register`

ou equivalente coerente com a convenção de API existente.

O endpoint será público.

Ao final da operação:

1. email é validado
2. email é normalizado
3. senha é validada
4. senha é convertida em hash
5. usuário é persistido
6. resposta segura é retornada

O usuário NÃO deverá ser autenticado automaticamente nesta TASK.

---

# 3. Request

Crie DTO específico.

Exemplo conceitual:

`RegisterUserRequest`

Campos:

- email
- password

Não utilizar entidade `User` como request.

---

# 4. Email

Valide:

- obrigatório
- não vazio
- formato válido
- tamanho máximo compatível com o modelo

Utilize Jakarta Bean Validation quando apropriado.

A validação HTTP não substitui constraints do banco.

---

# 5. Normalização

Reutilize EXATAMENTE a política estabelecida na TASK-1.1.

Não implemente uma segunda estratégia.

A normalização deve ocorrer antes de:

- verificar existência
- persistir

Exemplo:

` Bill@Example.com `

deverá seguir a política documentada e resultar no mesmo identificador lógico que:

`bill@example.com`

Não aplicar regras específicas de Gmail ou outros provedores.

---

# 6. Senha

Valide utilizando a política implementada na TASK-1.2.

Não duplique regras manualmente no controller.

Não aplicar `trim()` à senha.

Não modificar casing.

Não registrar senha.

---

# 7. Hash

Antes de persistir:

raw password
↓
PasswordService/PasswordEncoder
↓
passwordHash
↓
User

Nunca persistir raw password.

Nunca retornar raw password.

Nunca retornar passwordHash.

---

# 8. Caso de uso

Implemente o cadastro através da camada de aplicação.

Exemplo conceitual:

`RegisterUserService`

ou:

`RegisterUserUseCase`

Siga a nomenclatura existente.

O controller NÃO deverá:

- acessar repository diretamente
- executar hash diretamente
- implementar normalização
- possuir regra de negócio

Controller deve apenas:

1. receber request
2. validar contrato HTTP
3. delegar ao caso de uso
4. devolver resposta

---

# 9. Transação

O cadastro deverá executar em contexto transacional apropriado.

Utilize `@Transactional` na camada de aplicação quando coerente.

Não coloque `@Transactional` no controller.

---

# 10. Verificação de email existente

Antes da criação, consulte se o email normalizado já existe.

Isso permite resposta amigável.

Porém:

ESSA VERIFICAÇÃO NÃO É GARANTIA SUFICIENTE.

A constraint UNIQUE do banco continua sendo a proteção definitiva contra race conditions.

---

# 11. Concorrência

Considere o cenário:

Request A verifica email → livre
Request B verifica email → livre
Request A insere
Request B tenta inserir

O segundo request deverá resultar em:

`409 Conflict`

e não:

`500 Internal Server Error`

Trate adequadamente a violação de unicidade relacionada ao email.

Não transforme genericamente qualquer erro de banco em 409.

---

# 12. Email duplicado

Para email já cadastrado, retorne:

`409 Conflict`

utilizando a infraestrutura Problem Details existente.

Mensagem conceitual:

"An account with this email already exists."

Adapte o idioma às convenções atuais da API.

Não informe dados adicionais sobre a conta existente.

---

# 13. Response

Crie DTO específico.

Exemplo:

`RegisteredUserResponse`

Retorne apenas informações seguras necessárias.

Sugestão:

- id
- email
- createdAt

Não retornar:

- password
- passwordHash
- active, salvo necessidade clara
- detalhes internos

---

# 14. HTTP Status

Cadastro bem-sucedido:

`201 Created`

Não utilizar `200 OK` por conveniência.

Quando apropriado, forneça header:

`Location`

apontando para a representação futura do recurso.

Porém, NÃO crie um endpoint GET fictício apenas para justificar `Location`.

Se ainda não houver recurso público consultável, documente a decisão.

---

# 15. Validação inválida

Requests inválidos deverão utilizar a infraestrutura existente da TASK-0.6.

Exemplos:

email ausente
→ 400

email inválido
→ 400

senha abaixo do mínimo
→ 400

senha acima do máximo
→ 400

senha somente espaços
→ 400

A resposta deve utilizar Problem Details e erros de campo quando apropriado.

---

# 16. Política de mensagens

Não retornar a senha em mensagens.

Não retornar o hash.

Não retornar stack trace.

Não retornar SQL.

Não retornar nome de constraint do banco.

---

# 17. Spring Security

Atualize a configuração de segurança SOMENTE o necessário para permitir:

`POST /api/auth/register`

sem autenticação.

Não abra:

`/api/**`

inteiro.

Mantenha Actuator/OpenAPI conforme política da Sprint 0.

---

# 18. CSRF

Analise a configuração atual antes de alterar CSRF.

Como a estratégia de autenticação ainda não foi finalizada, não desabilite proteções indiscriminadamente apenas para fazer o endpoint funcionar.

Documente qualquer decisão necessária.

A estratégia definitiva será revisitada com JWT.

---

# 19. CORS

Preserve a configuração existente.

Não adicione `*` para permitir o cadastro.

Frontend de cadastro ainda não existe.

---

# 20. Rate limiting

NÃO implemente infraestrutura complexa de rate limiting nesta TASK.

Entretanto, registre como requisito de segurança futuro para endpoints públicos sensíveis, especialmente:

- register
- login
- recuperação de senha

Não introduza Redis apenas para isso.

---

# 21. Confirmação de email

NÃO implemente verificação/confirmação de email nesta TASK.

O usuário criado ficará ativo conforme a política atual do modelo.

Confirmação de email poderá ser adicionada futuramente.

Não invente token de confirmação.

---

# 22. Captcha

Pode ser considerado futuramente caso abuso real justifique.

- request
- 201

Não documente login ou JWT ainda.

- normaliza email
- valida senha
- gera hash
- persiste usuário

### Email existente

- rejeita cadastro
- produz conflito apropriado

### Senha inválida

- não persiste usuário

### Segurança

- raw password não é usada como passwordHash

Utilize mocks quando o objetivo for testar somente o caso de uso.

- password

### 400 — email inválido

### 400 — senha inválida

### 409 — email existente
