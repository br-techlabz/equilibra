# TASK-7.3 — BACKEND DE COMPROMISSOS FUTUROS E EFETIVAÇÃO FINANCEIRA

PROJETO: EQUILIBRA
SPRINT: 7 — PREVISIBILIDADE FINANCEIRA
STACK: Spring Boot 4 + MySQL
SEGURANÇA: JWT + CurrentUser
QUALIDADE: Flyway + OpenAPI + Testcontainers/MySQL

CONTEXTO

Sprints 0 a 6 aprovadas.
TASK-7.0 — Arquitetura e ADR concluídos.
TASK-7.1 — Backend de Recorrências concluído.
TASK-7.2 — Frontend de Recorrências concluído.

OBJETIVO

Implementar o backend de compromissos financeiros
futuros e o fluxo controlado de efetivação financeira,
conforme o ADR da TASK-7.0.

Permitir administrar ocorrências previstas de
despesas e receitas, com vencimento, estados
e vinculação opcional a regras de recorrência,
se o ADR assim determinar.

Garantir que previsões não alterem o ledger.

Somente uma efetivação válida pode criar
a transação financeira real correspondente.

NÃO implementar frontend nesta tarefa.

==================================================

Preservar três conceitos distintos:

regra periódica.

FinancialCommitment / Occurrence:
compromisso previsto.

transação efetivada.

Usar nomes reais definidos no ADR.

Não tratar previsão como transação efetiva.

==================================================
6. COMPROMISSOS MANUAIS
==================================================

Se aprovados:

permitir compromisso único sem recorrência.

Não exigir recurrenceRuleId.

Se não aprovados:

não criar endpoint de compromisso avulso.

==================================================
7. COMPROMISSOS RECORRENTES
==================================================

Se previstos:

vincular ocorrência à regra correta.

Preservar identidade da ocorrência.

Não gerar duas ocorrências equivalentes
para a mesma regra e período.

==================================================
8. VALORES MONETÁRIOS
==================================================

Usar BigDecimal.

DECIMAL(19,2).

Rejeitar valores inválidos.

Não usar float/double.

Não arredondar silenciosamente.

==================================================
9. VENCIMENTO
==================================================

Usar LocalDate para dueDate.

Não confundir vencimento com occurredAt.

Respeitar timezone e calendário do ADR.

==================================================
10. ESTADOS
==================================================

Implementar estados aprovados.

Exemplos conceituais:

PENDING;
SETTLED;
CANCELLED.

OVERDUE pode ser derivado da data,
conforme ADR.

Não persistir estado derivado sem necessidade.

==================================================
11. TRANSIÇÕES
==================================================

Centralizar transições no service.

Não permitir:

efetivar compromisso cancelado;
efetivar duas vezes;
editar indevidamente compromisso efetivado;
cancelar sem política aprovada.

==================================================
12. GERAÇÃO DE OCORRÊNCIAS
==================================================

Se prevista na TASK-7.3:

usar mecanismo definido no ADR.

Não criar scheduler novo se o ADR
determinar geração sob demanda.

Não gerar ocorrências infinitas.

==================================================
13. HORIZONTE
==================================================

Respeitar limite aprovado.

Evitar geração massiva.

Aplicar filtros por owner e período.

==================================================
14. IDEMPOTÊNCIA DE GERAÇÃO
==================================================

Garantir unicidade por identidade
de ocorrência definida no ADR.

Executar geração repetida:

não pode duplicar compromissos.

Proteger também no banco.

==================================================
15. EDIÇÃO DE OCORRÊNCIA
==================================================

Se permitida:

editar somente campos aprovados.

Preservar relação com regra.

Não alterar transações já efetivadas.

==================================================
16. EDIÇÃO DA REGRA
==================================================

Validar efeitos sobre ocorrências futuras.

Não reescrever compromissos efetivados.

Não apagar histórico.

==================================================
17. PAUSA DE RECORRÊNCIA
==================================================

Respeitar política do ADR para:

novas ocorrências;
ocorrências existentes;
ocorrências vencidas;
ocorrências efetivadas.

==================================================
18. CANCELAMENTO DA REGRA
==================================================

Não cancelar transações financeiras reais.

Ocorrências futuras devem seguir
política aprovada.

==================================================
19. EFETIVAÇÃO FINANCEIRA
==================================================

Implementar operação atômica.

A efetivação deve:

1. Validar owner.
2. Validar estado do compromisso.
3. Validar conta e categoria.
4. Validar valor e data efetiva.
5. Criar transação financeira real usando
   serviços existentes.
6. Criar movimentos de ledger corretos.
7. Vincular compromisso à transação.
8. Alterar estado do compromisso.
9. Confirmar tudo em uma transação de banco.

Se falhar qualquer etapa:

rollback integral.

Não criar lógica paralela de ledger.

==================================================
20. DESPESA EFETIVADA
==================================================

Para EXPENSE:

usar fluxo real de Expense existente.

Gerar movimento negativo na conta
conforme arquitetura do ledger.

Não debitar conta duas vezes.

==================================================
21. RECEITA EFETIVADA
==================================================

Para INCOME:

usar fluxo real de Income existente.

Gerar movimento positivo na conta.

Não creditar duas vezes.

==================================================
22. DATA DE EFETIVAÇÃO
==================================================

Usar occurredAt conforme regra aprovada.

Não usar automaticamente dueDate
como occurredAt sem decisão explícita.

==================================================
23. VALOR EFETIVADO
==================================================

Se valor real puder diferir do previsto:

validar e persistir conforme ADR.

Não alterar plannedAmount silenciosamente.

Manter rastreabilidade.

==================================================
24. PAGAMENTO PARCIAL
==================================================

Se aprovado:

implementar modelo explícito.

Se não aprovado ou adiado:

não simular pagamento parcial
com estados inconsistentes.

Registrar fora do escopo.

==================================================
25. DUPLA EFETIVAÇÃO
==================================================

Duas chamadas para efetivar
o mesmo compromisso não podem
gerar duas transações reais.

Aplicar:

- constraint;
- locking;
- verificação transacional;
- idempotência aprovada.

Não depender apenas de botão desabilitado
no frontend.

==================================================
26. RETRY
==================================================

não criar lançamento duplicado.

Definir resposta conforme contrato
e semântica de idempotência.
