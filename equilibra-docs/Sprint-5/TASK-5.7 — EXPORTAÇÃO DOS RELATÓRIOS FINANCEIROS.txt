# TASK-5.7 — EXPORTAÇÃO DOS RELATÓRIOS FINANCEIROS

PROJETO: Equilibra
SPRINT: 5 — Relatórios Financeiros
STACK: Spring Boot 4 + Angular 19 + MySQL

CONTEXTO
TASK-5.0 — ADR dos relatórios concluído.
TASK-5.1 — Backend do Relatório Financeiro concluído.
TASK-5.2 — Verificar status real no repositório.

TASK-5.5 — Backend do Relatório de Auditoria concluído.
TASK-5.6 — Interface do Relatório de Auditoria concluída.

OBJETIVO

Implementar exportação dos três relatórios:

1. Relatório Financeiro
2. Relatório por Categoria
3. Relatório de Auditoria

Formatos:
- PDF
- CSV

Os arquivos devem representar exatamente os filtros aplicados
e as regras financeiras já existentes.

Não implementar XLSX nesta TASK, salvo se o ADR 5.0 exigir.

PRINCÍPIO CENTRAL:

A exportação é uma REPRESENTAÇÃO dos read models existentes.
Ela não deve criar uma segunda implementação das regras financeiras.

==================================================
5. FILTROS
==================================================

Cada exportação deve aceitar exatamente os filtros
aplicáveis ao relatório de origem.

Financeiro:
- período;
- contas;
- demais filtros aprovados.

Categoria:
- período;
- contas;
- categorias/tags, somente se suportadas.

Auditoria:
- período;
- contas;
- tipo;
- status;
- categorias/tags, se suportados;
- ordenação, se suportada.

Não aceitar ownerId.

Não inventar filtros adicionais.

==================================================
6. SEMÂNTICA TEMPORAL
==================================================

Preservar occurredAt e intervalo definidos no ADR.

Se [from,to):

from incluído;
to excluído.

O PDF/CSV deve identificar claramente o período
selecionado pelo usuário.

Evitar divergência por timezone.

==================================================
7. CONTAS
==================================================

Exportação deve respeitar:

- todas as contas;
- uma conta;
- múltiplas contas;
- contas inativas históricas conforme ADR.

IDs estrangeiros ou inexistentes devem receber
tratamento seguro conforme política atual.

Transferências entre duas contas selecionadas
não podem aparecer duplicadas.

==================================================
8. RELATÓRIO FINANCEIRO
==================================================

Exportar conforme contrato real:

- período;
- contas selecionadas;
- saldo inicial;
- receitas;
- despesas;
- resultado financeiro;
- transferências internas;
- transferências de entrada na seleção;
- transferências de saída da seleção;
- variação do saldo;
- saldo final;
- detalhamento por conta, se existente;
- movimentações detalhadas, se previstas.

Invariante:

Saldo final = Saldo inicial + Variação do saldo.

Transferências não podem ser classificadas como
receita ou despesa.

==================================================
9. RELATÓRIO POR CATEGORIA
==================================================

Exportar:

- período;
- contas;
- resumo de receitas;
- resumo de despesas;
- resultado;
- agrupamentos por categoria;
- percentuais, se existentes.

Categoria BOTH:

receitas e despesas separadas.

Categorias inativas históricas:

preservadas.

Sem categoria:

usar agrupamento real.

Transferências:

não incluídas nos totais de receitas/despesas.

==================================================
10. RELATÓRIO DE AUDITORIA
==================================================

Exportar transações lógicas conforme filtros.

Incluir ACTIVE e CANCELLED conforme seleção.

Cada Transfer aparece UMA vez.

Não inventar histórico imutável de alterações.

Usar somente metadados reais disponíveis:

transactionId;
type;
status;
description;
amount;
occurredAt;
createdAt;
updatedAt;
account/source/destination;
category;
tags;
attachmentCount.

Selecionar apenas campos aprovados no ADR/API.

Não exportar bytes de anexos.

==================================================
11. PAGINAÇÃO DA AUDITORIA
==================================================

CRÍTICO.

A exportação deve representar TODO o conjunto filtrado,
não apenas a página atual.

Exemplo:

137 transações filtradas.
UI mostra 20.

CSV/PDF deve conter as 137 transações,
salvo limite explícito de segurança.

Não usar paginação client-side para exportar.

Não fazer N requests Angular para reunir páginas.

==================================================
12. EXPORTAÇÃO ESCALÁVEL
==================================================

Não carregar volume ilimitado de transações na memória.

Usar paginação interna em lotes, cursor ou streaming,
conforme arquitetura existente.

Para volumes grandes:

definir limite seguro de registros;
definir política de tamanho de arquivo;
definir tratamento de timeout;
documentar comportamento.

Não introduzir filas/background jobs nesta TASK
sem necessidade comprovada.

Se o limite for excedido:

retornar erro claro e seguro, conforme contrato.

Não gerar arquivo parcial silenciosamente.

==================================================
13. ORDENAMENTO
==================================================

Auditoria deve preservar a ordenação determinística
do backend.

Preferência:

occurredAt DESC + id DESC,

se essa for a ordenação aprovada.

Lotes de exportação não podem:

duplicar;
omitir;
reordenar indevidamente.

==================================================
14. CSV — FORMATO
==================================================

Gerar CSV compatível com Excel/LibreOffice.

Requisitos:

- UTF-8;
- cabeçalho;
- nomes de colunas em português;
- valores monetários consistentes;
- datas consistentes;
- delimitador documentado;
- escaping correto de aspas, delimitadores e quebras de linha.

Considerar BOM UTF-8 se necessário para compatibilidade,
conforme convenção do projeto.

Definir estratégia explícita para valores decimais,
evitando ambiguidades de localidade.

Não converter BigDecimal para double.

==================================================
15. CSV — SEGURANÇA
==================================================

Proteger contra CSV Formula Injection.

Campos controlados pelo usuário podem começar com:

=
+
-
@
tab
CR
LF

Aplicar neutralização segura a campos textuais
não confiáveis antes da serialização.

Não alterar os dados persistidos.

Testar descrições, nomes de contas, categorias,
tags e observações maliciosas.

==================================================
16. CSV — CONSISTÊNCIA
==================================================

Uma linha por agrupamento no relatório por categoria.

Uma linha por transação lógica na auditoria.

Para o relatório financeiro, definir estrutura clara
para resumo e detalhamento conforme ADR.

Não gerar linhas duplicadas por joins com tags/anexos.

==================================================

Criar PDF profissional, legível e consistente
com a identidade visual do Equilibra.

- indicadores;

Saldo inicial;

Transferências;

==================================================
20. PDF — AUDITORIA
==================================================

Apresentar tabela de transações com colunas essenciais.

Se houver muitas colunas:

reduzir colunas com critério;
ou distribuir informações em linhas complementares.

Não truncar dados importantes silenciosamente.

Suportar múltiplas páginas.

Repetir cabeçalho da tabela quando adequado.

==================================================
21. PDF — QUALIDADE
==================================================

Testar:

- textos longos;
- valores monetários grandes;
- nomes extensos;
- múltiplas páginas;
- caracteres acentuados;
- categorias inativas;
- transações canceladas;
- ausência de dados;
- páginas sem conteúdo cortado.

Utilizar biblioteca adequada ao ecossistema Java,
preferencialmente uma já aprovada no projeto.

Verificar licença e manutenção da biblioteca antes
de adicionar dependência.

==================================================
22. PDF — SEGURANÇA
==================================================

Não incluir:

JWT;
storageKey;
filesystem path;
stack trace;
dados de outro usuário;
metadados privados internos.

Escapar/sanitizar texto conforme mecanismo da biblioteca.

Não permitir HTML externo ou recursos remotos
não confiáveis durante a renderização.

==================================================
23. HEADERS HTTP
==================================================

Configurar Content-Type correto:

application/pdf

text/csv; charset=UTF-8

Content-Disposition:

attachment; filename=...

Usar filenames previsíveis e seguros.

Exemplos:

equilibra-financeiro-2026-10.pdf
equilibra-categorias-2026-10.csv
equilibra-auditoria-2026-10.pdf

Não usar dados do usuário sem sanitização no filename.

==================================================
24. CACHE E PRIVACIDADE
==================================================

Exportações contêm informações financeiras privadas.

Aplicar política HTTP apropriada:

Cache-Control: no-store

e demais headers necessários conforme
infraestrutura de segurança existente.

Não armazenar arquivos exportados em diretório público.

Se geração temporária for necessária:

usar local privado;
limpar após uso;
não deixar órfãos.

==================================================
25. AUTENTICAÇÃO
==================================================

JWT obrigatório.

Identidade vem de CurrentUser.

Nenhum endpoint público de exportação.

Não enviar JWT por query string.

==================================================
26. OWNERSHIP
==================================================

Todas as consultas devem permanecer owner-scoped.

User A nunca exporta dados de User B.

Validar IDs de contas, categorias e tags
conforme política existente.

Não permitir IDOR/BOLA.

28. FRONTEND — FILTROS APLICADOS
==================================================

CRÍTICO.

Exportar exatamente appliedFilters.

Nunca exportar draftFilters ainda não aplicados.

Exemplo:

Relatório exibido: setembro.
Usuário alterou draft para outubro.
Ainda não clicou Aplicar.

Exportação deve usar setembro.

==================================================
29. FRONTEND — DOWNLOAD
==================================================

responseType: blob.

Criar objectURL temporária para download.

Revogar objectURL após uso.

Não usar window.open com token na URL.

Não usar links públicos diretos.
