# PARTE A — TAGS

# 7. CONCEITO DE TAG

Definir formalmente o conceito.

Tag é um rótulo livre criado pelo usuário para organização transversal
das transações.

Exemplos:

viagem
trabalho
família
reembolsável
urgente

---

# 8. TAG NÃO É CATEGORY

Deixar explicitamente documentado:

Category = classificação financeira principal.

Tag = marcador organizacional adicional.

Não substituir Category por Tag.

---

# 9. TAG NÃO ALTERA FINANÇAS

Tag não possui efeito financeiro.

---

# 10. OWNERSHIP

Toda Tag pertence a exatamente um usuário.

Conceitualmente:

Tag
- id
- ownerId
- name
- normalizedName
- active
- createdAt
- updatedAt

Avalie campos reais necessários.

---

# 11. ID

Usar padrão UUID existente.

Não introduzir outro padrão.

---

# 12. NAME

Definir:

- obrigatório;
- trim;
- não vazio;
- tamanho máximo.

Preferência inicial:

100 caracteres

se consistente com Category.

---

# 13. NORMALIZATION

Reutilizar política de normalização já utilizada por:

AssetAccount
Category.

No mínimo:

trim
+
case-insensitive uniqueness.

---

# 14. ACENTOS

Não remover acentos automaticamente sem política global existente.

Exemplo:

"Viagem São Paulo"

deve preservar apresentação original.

---

# 15. UNIQUE

Mesmo owner não pode possuir duas Tags ATIVAS com mesmo nome
normalizado.

Exemplo:

Viagem
viagem
 VIAGEM

devem colidir.

---

# 16. CROSS USER

User A pode ter:

Viagem

e User B também.

---

# 17. ACTIVE

Avalie manter:

active = true/false

seguindo Category/AssetAccount.

Preferência:

sim.

---

# 18. MOTIVO

Tag desativada:

- permanece no histórico;
- não fica disponível para novas associações;
- pode ser reativada.

---

# 19. DELETE

Preferência:

não realizar physical delete como fluxo normal.

---

# 20. TAG ASSOCIATION

Uma transação pode possuir:

0..N Tags.

Uma Tag pode estar associada a:

0..N transações.

Relação:

many-to-many.

---

# 21. TRANSACTION TYPES

Tags devem poder ser associadas a:

EXPENSE
INCOME
TRANSFER.

---

# 22. TRANSFER

Uma Transfer possui conjunto único de Tags.

NÃO:

Tags da source
+
Tags da destination.

Transfer é uma única transação lógica.

---

# 23. LEDGER MOVEMENT

Tag deve pertencer à transação lógica.

NÃO ao AccountMovement individual.

---

# 24. MODELAGEM

Se existe FinancialTransaction como entidade central:

avaliar associação Tag ↔ FinancialTransaction.

Isso tende a ser preferível.

Mas confirme modelo real.

---

# 25. JOIN TABLE

Definir tabela de associação conceitual:

financial_transaction_tags

ou nomenclatura coerente.

Campos esperados:

transaction_id
tag_id

Avalie constraints.

---

# 26. UNIQUE ASSOCIATION

Mesma Tag não pode ser associada duas vezes à mesma transação.

---

# 27. CROSS-OWNER ASSOCIATION

CRÍTICO:

FinancialTransaction de User A nunca pode receber Tag de User B.

---

# 28. DEFENSE IN DEPTH

Não confiar apenas no frontend.

Application/domain deve validar ownership.

Avalie constraints possíveis no banco.

---

# 29. INACTIVE TAG

Definir política.

Preferência:

Tag inativa:

- continua aparecendo em transações históricas;
- não pode ser adicionada a nova transação;
- associação histórica não é removida.

---

# 30. REMOVE TAG FROM TRANSACTION

Remover associação:

não remove Tag.

Apenas remove vínculo.

---

# 31. CANCELLED TRANSACTION

Definir se Tags permanecem.

Preferência:

SIM.

Cancelamento financeiro não apaga metadados históricos.

---

# 32. EDIT TAGS ON CANCELLED

Decidir formalmente.

Preferência arquitetural:

# 33. TAG LIMIT

Avalie limite de Tags por transação.

Não criar limite arbitrário sem necessidade.

# 34. TAG COLOR

# 35. TAG ICON

# PARTE B — ATTACHMENTS

# 40. CONCEITO

Attachment é um arquivo pertencente a uma transação.

Exemplos:

- nota fiscal;
- recibo;
- comprovante;
- boleto;
- screenshot;
- documento PDF.

---

# 41. TRANSACTION TYPES

Attachments devem funcionar para:

EXPENSE
INCOME
TRANSFER.

---

# 42. ATTACHMENT NÃO É MOVEMENT

Attachment pertence à transação lógica.

Não ao movement individual.

---

# 43. CARDINALIDADE

O requisito original mencionava "anexo".

Precisamos decidir se:

A) exatamente 0..1 arquivo

ou

B) 0..N arquivos.

Escolha arquitetural recomendada:

0..N Attachments por transação.

Justifique.

---

# 44. MOTIVO PARA 0..N

Um lançamento pode possuir:

- nota fiscal;
- comprovante;
- recibo;
- imagem complementar.

Modelar 0..N evita migração estrutural futura.

Mas mantenha UX inicial simples.

---

# 45. ATTACHMENT ENTITY

Definir entidade conceitual.

Exemplo:

TransactionAttachment
- id
- ownerId
- transactionId
- originalFileName
- storedFileName ou storageKey
- contentType
- sizeBytes
- checksum
- createdAt

Avalie campos reais.

---

# 46. NÃO ARMAZENAR PATH ABSOLUTO

Não persistir:

/home/user/project/uploads/...

Persistir identificador lógico:

storageKey.

---

# 47. STORAGE KEY

Deve ser gerado pelo servidor.

Nunca confiar no nome enviado pelo cliente.

Exemplo conceitual:

user/{ownerUuid}/transactions/{transactionUuid}/{attachmentUuid}

Não é obrigatório usar exatamente esse formato.

---

# 48. ORIGINAL FILE NAME

Pode ser armazenado apenas como metadata de apresentação.

---

# 49. SEGURANÇA DO FILE NAME

Nunca usar originalFileName diretamente como path físico.

---

# 50. PATH TRAVERSAL

Bloquear ataques como:

../../etc/passwd

..\..\secret

nomes Unicode maliciosos equivalentes.

---

# 51. STORAGE ABSTRACTION

Criar decisão arquitetural para uma interface conceitual:

FileStorage
ou
AttachmentStorage.

Exemplos de operações:

store(...)
open(...)
delete(...)

Não implementar necessariamente agora.

---

# 52. OBJETIVO DA ABSTRAÇÃO

Permitir:

DEV:

FUTURO:
S3
MinIO
object storage.

---

# 53. NÃO ACOPLAR DOMÍNIO AO FILESYSTEM

Domain/Application não deve conhecer:

java.nio.file.Path

como regra de negócio.

---

# 54. PRIMEIRA IMPLEMENTAÇÃO

Avalie melhor opção para MVP.

Preferência:

filesystem local configurável em DEV/MVP,

atrás de Storage abstraction.

---

# 55. PRODUÇÃO

Documentar claramente:

filesystem local em uma única instância não é arquitetura final ideal
para ambiente distribuído/container efêmero.

---

# 56. FUTURE STORAGE

Planejar compatibilidade com:

S3-compatible object storage.

Não implementar integração cloud agora.

---

# 57. DATABASE BLOB

Avalie explicitamente:

---

# 58. RECOMENDAÇÃO

Preferência:

metadata no MySQL
+

Evitar BLOB no banco para anexos comuns.

Justifique tecnicamente.

# 59. METADATA SOURCE

MySQL é fonte de verdade para metadata/autorização.

Storage é fonte dos bytes.

---

# 60. ATOMICIDADE

e

---

# 61. UPLOAD FLOW

Definir fluxo seguro.

Exemplo conceitual:

1. validar usuário;
2. localizar transaction por owner;
3. validar status/política;
4. validar arquivo;
5. gerar attachmentId/storageKey;
6. gravar storage;
7. persistir metadata;
8. se DB falhar, remover arquivo;
9. retornar metadata.

Ou estratégia equivalente.

---

# 62. DB FAILURE AFTER STORE

Não deixar arquivo órfão silenciosamente.

Definir compensação.

---

# 63. STORAGE FAILURE

Não persistir metadata apontando para arquivo inexistente.

---

# 64. DELETE FLOW

---

# 65. PREFERÊNCIA
