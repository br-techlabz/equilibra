As TASK-1.1 até TASK-1.7 foram concluídas.

**Sprint 1 — Identidade, Usuários e Autenticação**

- tela de login

# 16. Token — decisão obrigatória

Nesta TASK, o access token deve permanecer SOMENTE EM MEMÓRIA.

É PROIBIDO armazená-lo em:

- localStorage
- sessionStorage
- IndexedDB
- cookie JavaScript
- arquivo
- URL
- query parameter

Não criar persistência silenciosa.

---

# 17. Consequência da estratégia

Como não existe refresh token e o access token vive apenas em memória:

**recarregar a página encerra a sessão do frontend.**

Esse comportamento é ACEITO nesta fase.

Documente explicitamente.

Não tente contornar armazenando JWT no browser.

---

# 18. Não decodificar JWT para confiar em identidade

O frontend não deve utilizar payload JWT como fonte autoritativa do perfil.

Após login:

1. receba token
2. utilize token para chamar `/api/users/me`
3. obtenha usuário atual do backend

O `/me` é a fonte da representação atual do usuário.

---

# 19. JWT parsing

Evite adicionar biblioteca para decodificar JWT.

O frontend não precisa validar criptograficamente o token.

Essa responsabilidade é do backend.

---

Envie:

somente na operação necessária para carregar `/me`.

NÃO crie ainda interceptor global.

Deixe a estrutura preparada para remover essa lógica localizada na TASK-1.9.

# 21. Sequência do login

Fluxo obrigatório:

1. usuário envia formulário
2. estado = authenticating
3. POST login
4. recebe access token
5. guarda token em memória
6. GET `/me`
7. recebe usuário
8. guarda usuário em memória
9. estado = authenticated
10. navega para área principal

---

# 22. Falha ao carregar `/me`

Se login retornar token válido, mas `/me` falhar:

- NÃO considerar autenticação concluída
- limpar token da memória
- limpar currentUser
- voltar para estado unauthenticated
- apresentar erro apropriado

Não deixar estado parcialmente autenticado.

---

# 33. Token encapsulado

Evite expor publicamente o token como Signal mutável.

O token deve permanecer encapsulado no AuthService.

Quando a TASK-1.9 implementar interceptor, forneça uma forma mínima e controlada de obter o access token.

Não permita que componentes alterem token diretamente.

---

# 34. Expiração

O backend retorna `expiresIn`.

Armazene metadados necessários em memória se forem úteis.

Não implemente refresh automático.

Não implemente timer complexo.

Na TASK-1.9, respostas 401 de APIs protegidas poderão limpar a sessão.

---

# 35. Token expirado durante sessão

Não implemente renovação.

Se token expirar, a aplicação futuramente deverá retornar ao login.

A infraestrutura completa desse comportamento será finalizada na TASK-1.9.

- apaga token em memória

NÃO implemente ainda botão/fluxo completo de logout.

---

# 37. Reload
