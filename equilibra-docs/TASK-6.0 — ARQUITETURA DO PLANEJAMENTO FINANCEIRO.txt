==================================================
4. REGRAS DE CATEGORIA
==================================================

Categorias existentes possuem applicability:

EXPENSE
INCOME
BOTH.

Definir:

EXPENSE:
elegível para orçamento de despesa.

BOTH:
elegível para orçamento de despesa.

INCOME:
não elegível para orçamento de despesa.

Confirmar essa política com o modelo real.

Uma categoria BOTH deve considerar apenas suas
transações EXPENSE para consumo do orçamento.

Receitas não podem reduzir artificialmente o gasto realizado.

==================================================
5. COMPETÊNCIA MENSAL
==================================================

Definir representação canônica do mês:

year + month

ou YearMonth no domínio Java.

Evitar armazenar datas artificiais sem necessidade.

Exemplo:

2026-10.

Definir claramente timezone e conversão para intervalo
de occurredAt.

Se o período mensal for:

[primeiro instante do mês,
 primeiro instante do mês seguinte)

documentar a regra.

==================================================
6. ORÇAMENTO E CONTA
==================================================

Decidir se orçamento é:

A. global por categoria, somando todas as contas do usuário;

ou

B. associado a categorias e subconjuntos de contas.

RECOMENDAÇÃO:

MVP global por categoria.

Justificativa:

- evita duplicação de orçamento;
- simplifica acompanhamento;
- preserva a semântica da categoria;
- facilita conciliação com Relatório por Categoria.

Se existir requisito real para orçamento por conta,
documentar como extensão futura.

Não usar float/double.

Rejeitar mais de duas casas decimais,
conforme política monetária existente.

==================================================
11. REALIZADO
==================================================

Definir:

actualAmount = soma de despesas ACTIVE
da categoria
no mês correspondente.

A consulta deve ser owner-scoped.

Usar occurredAt.

Não usar createdAt como competência financeira.

==================================================
12. CANCELAMENTOS
==================================================

Expense CANCELLED:

não contribui para actualAmount.

Cancelamento deve atualizar o valor realizado
automaticamente nas consultas posteriores.

Não armazenar actualAmount como verdade mutável
sem justificativa arquitetural.

==================================================
13. TRANSFERÊNCIAS
==================================================

Transferências:

não consomem orçamento de despesa.

Não converter transferência em despesa.

Não contar transferências internas ou entre contas
como gasto orçamentário.

==================================================
14. RECEITAS
==================================================

Receitas:

não consomem orçamento de despesa.

Para categoria BOTH:

somente Expense contribui para actualAmount.

Não calcular orçamento líquido de receitas menos despesas
sem requisito explícito.

==================================================
15. TRANSAÇÕES SEM CATEGORIA
==================================================

Inspecionar se despesas sem categoria são permitidas.

Se sim, definir política:

- agrupamento "Sem categoria";
- orçamento específico;
- exclusão do acompanhamento por categoria;
- indicador separado de gastos não categorizados.

Não inventar categoria persistida automaticamente.

==================================================
16. INDICADORES
==================================================

Definir DTOs para:

plannedAmount;
actualAmount;
remainingAmount;
consumptionPercentage;
budgetStatus.

Fórmulas propostas:

remainingAmount = plannedAmount - actualAmount.

consumptionPercentage =
actualAmount / plannedAmount * 100.

Para plannedAmount=0:

definir semântica explícita.

Não dividir por zero.

Não truncar consumo acima de 100%.

==================================================
17. STATUS DO ORÇAMENTO
==================================================

Propor estados derivados:

ON_TRACK
WARNING
EXCEEDED

Exemplo inicial:

ON_TRACK:
consumo abaixo de 80%.

WARNING:
consumo de 80% até 100%.

EXCEEDED:
consumo acima de 100%.

IMPORTANTE:

Os limiares são propostas, não regras já aprovadas.

Definir no ADR:

- se 100% é WARNING ou LIMIT_REACHED;
- se 0% é ON_TRACK;
- tratamento de plannedAmount=0;
- se limiares são configuráveis;
- se status é persistido ou derivado.

Preferir status derivado.
