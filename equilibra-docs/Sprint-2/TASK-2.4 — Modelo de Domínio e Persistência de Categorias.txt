# 2. Conceito

Uma Category representa uma classificação financeira utilizada para
organizar transações.

Exemplos:

Despesas:

- Alimentação
- Moradia
- Transporte
- Saúde
- Educação
- Lazer

Receitas:

- Salário
- Freelance
- Investimentos
- Reembolsos

Uma categoria NÃO representa:

- conta bancária;
- conta de ativo;
- transação;
- tag;
- favorecido;
- credor.

---

# 3. Nome de domínio

Utilize:

Category

ou nomenclatura equivalente já consistente com a arquitetura.

Não use FinancialCategory, TransactionCategory ou outros nomes mais
complexos sem necessidade real.

# 6. Ownership

Toda categoria criada pelo usuário pertence exclusivamente a ele.

Uma categoria de A jamais poderá ser utilizada ou acessada por B.

Prepare o domínio/persistência para consultas:

ownerId + resourceId

seguindo o padrão de segurança estabelecido em AssetAccount.

---

# 7. Owner

Avalie se o projeto utiliza:

UUID ownerId

ou:

@ManyToOne User

em AssetAccount.

Para Category, siga a mesma decisão salvo motivo técnico forte.

Não introduza padrão diferente sem justificativa.

---

# 8. Nome

Campo:

name

Requisitos:

- obrigatório;
- trim;
- não vazio;
- limite razoável.

Preferência:

100 caracteres

ou o mesmo limite adotado em AssetAccount quando apropriado.

# 9. Normalização

Utilize estratégia coerente com AssetAccount.

No mínimo:

- trim;
- comparação case-insensitive.

Exemplo:

"Alimentação"
" alimentação "
"ALIMENTAÇÃO"

devem ser tratados de maneira consistente.

# 10. Unicode

separados.

# 11. Aplicabilidade

Uma categoria poderá ser utilizada para:

- despesas;
- receitas;
- ambos.

Crie enum conceitual:

com valores:

EXPENSE
INCOME
BOTH

Se houver nome melhor consistente com o projeto, pode utilizá-lo,
documentando a decisão.

# 12. Significado

Exemplos:

Alimentação
Moradia
Transporte

INCOME

Categoria destinada a receitas.

Exemplos:

Salário
Freelance

BOTH

Exemplo:

Outros

# 13. Por que não booleanos

NÃO modele como:

isExpense

# 14. Persistência do enum

EXPENSE
INCOME
BOTH

# 15. active

# 16. Desativação

Categorias devem suportar desativação lógica.

Categoria inativa:

- permanece persistida;
- mantém histórico futuro;
- poderá continuar associada a transações antigas;
- não deverá aparecer futuramente como opção para novos lançamentos.

---

# 17. Exclusão física

NÃO implemente política de exclusão física como regra principal.

Categorias financeiras podem possuir histórico.

A estratégia principal será:

desativação.

---

# 19. Mesmo usuário

# 22. Applicability e unicidade

IMPORTANTE:

Nesta versão, o nome deve ser único entre categorias ativas do usuário
independentemente de applicability.

Portanto NÃO permitir simultaneamente:

Alimentação / EXPENSE
Alimentação / INCOME

como duas categorias diferentes.

Se o usuário quiser usar Alimentação nos dois contextos:

utilize:

Alimentação / BOTH

Isso evita duplicidade visual e ambiguidade.
