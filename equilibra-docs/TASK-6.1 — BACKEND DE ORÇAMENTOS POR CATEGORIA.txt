# TASK-6.1 — BACKEND DE ORÇAMENTOS POR CATEGORIA

PROJETO: EQUILIBRA
SPRINT: 6 — PLANEJAMENTO FINANCEIRO
STACK: Spring Boot 4 + MySQL + Angular 19

CONTEXTO

Sprint 5 aprovada.
TASK-6.0 concluída.
ADR, especificação funcional, contratos e roadmap da
Sprint 6 produzidos na TASK-6.0.

OBJETIVO

Implementar exclusivamente o backend de cadastro,
consulta, edição e remoção/arquivamento de orçamentos
mensais por categoria, conforme decisões da TASK-6.0.

Não implementar nesta etapa:

- frontend;
- cálculo de realizado;
- planejado versus realizado;
- dashboard de orçamento;
- alertas;
- metas financeiras.

O ADR 6.0 prevalece sobre todas as sugestões deste prompt.

==================================================
3. ENTIDADE DE DOMÍNIO
==================================================

Implementar a entidade aprovada no ADR.

Nome conceitual:

CategoryBudget

Campos candidatos:

id: UUID
ownerId: UUID
categoryId: UUID
year: integer
month: integer
plannedAmount: BigDecimal
createdAt
updatedAt

Não adicionar campos sem necessidade.

Não persistir actualAmount, remainingAmount
ou consumptionPercentage nesta TASK, salvo decisão
expressa do ADR.

==================================================
4. COMPETÊNCIA MENSAL
==================================================

Representar competência conforme ADR.

Preferência conceitual:

YearMonth

ou campos year + month.

Validar:

year permitido;
month entre 1 e 12;
competência válida;
formato de entrada.

Não converter competência em timestamp
sem necessidade.

==================================================
5. VALOR PLANEJADO
==================================================

Usar BigDecimal.

Persistência compatível com DECIMAL(19,2),
ou padrão monetário aprovado.

Rejeitar:

- null;
- valores negativos, se proibidos pelo ADR;
- mais de duas casas decimais;
- valores fora do limite da coluna;
- formatos inválidos.

Definir comportamento de zero conforme ADR.

Não arredondar silenciosamente valores inválidos.

==================================================
6. CATEGORIAS ELEGÍVEIS
==================================================

Respeitar applicability:

EXPENSE
INCOME
BOTH

Se ADR aprovou orçamento de despesas:

EXPENSE: elegível.
BOTH: elegível.
INCOME: não elegível.

Validar no backend.

Não confiar no frontend.

==================================================
7. CATEGORIAS INATIVAS
==================================================

Seguir política do ADR.

Cenários obrigatórios:

- categoria ativa na criação;
- categoria inativa na criação;
- categoria desativada após orçamento existente;
- consulta histórica;
- edição de orçamento histórico;
- categoria reativada.

Não excluir automaticamente orçamentos históricos
quando uma categoria for desativada.

==================================================
8. OWNERSHIP
==================================================

Toda operação deve derivar o usuário autenticado:

JWT -> SecurityContext -> CurrentUser.

Nunca aceitar ownerId em requests.

Validar categoryId pertencente ao usuário.

Categoria estrangeira deve ser tratada como
inexistente conforme política de segurança.

Buscar orçamento sempre por:

id + ownerId

ou estratégia equivalente.

Nunca usar findById isolado para autorizar operação.

==================================================
9. UNICIDADE
==================================================

Aplicar unicidade aprovada no ADR.

Exemplo conceitual:

UNIQUE(owner_id, category_id, year, month)

A constraint deve existir no MySQL.

Validar conflito também na camada de aplicação
para mensagem amigável.

Entretanto, a constraint do banco é obrigatória
para proteger contra concorrência.

==================================================
10. CONCORRÊNCIA
==================================================

Testar duas tentativas simultâneas de criação
para mesma categoria e competência.

Resultado esperado:

apenas um orçamento persistido.

A outra tentativa deve receber erro de domínio
consistente, preferencialmente 409.

Não permitir duplicatas.

==================================================
11. CRIAÇÃO
==================================================

Implementar endpoint conforme contrato ADR.

Exemplo conceitual:

POST /api/budgets

Request candidato:

{
  "categoryId": "UUID",
  "month": "2026-10",
  "plannedAmount": 1000.00
}

A estrutura final deve seguir OpenAPI/ADR real.

Resposta:

201 Created.

Location header quando padrão existente exigir.

Não receber ownerId.

==================================================
12. LISTAGEM
==================================================

Implementar endpoint conforme ADR.

Exemplo:

GET /api/budgets?month=2026-10

Permitir consultar orçamentos próprios.

Suportar filtros aprovados:

competência;
categoria;
status de arquivamento, se existir.

Não implementar filtros não previstos.

Retornar somente dados do usuário.

==================================================
13. DETALHAMENTO
==================================================

Endpoint conceitual:

GET /api/budgets/{id}

Retornar DTO tipado.

Incluir metadados da categoria se aprovados:

categoryId;
categoryName;
categoryActive.

Não expor entidades JPA.

==================================================
14. EDIÇÃO
==================================================

Endpoint conforme ADR.

Exemplo:

PUT /api/budgets/{id}

Se identidade category + month for imutável,
permitir editar somente plannedAmount.

Não permitir alteração silenciosa de:

ownerId;
categoryId;
competência.

Se ADR permitir outras alterações,
seguir exatamente as regras aprovadas.

==================================================
15. REMOÇÃO OU ARQUIVAMENTO
==================================================

Implementar política aprovada no ADR.

Não presumir soft delete.

Orçamentos são dados de planejamento,
não movimentos do ledger.

Se exclusão física for aprovada:

DELETE /api/budgets/{id}

Se arquivamento for aprovado:

usar endpoint e estado definidos no ADR.

Não inventar status ACTIVE/CANCELLED
copiados de FinancialTransaction.

==================================================
16. CATEGORIA RENOMEADA

Preferir relação com categoria real,
sem snapshot duplicado, salvo decisão contrária.

O orçamento deve continuar associado ao mesmo UUID.

18. ERROS HTTP
==================================================

Seguir convenção existente.

400:
request inválido.

401:
sem autenticação.

404:
orçamento/categoria inexistente ou estrangeiro.

409:
duplicidade ou conflito de estado,
quando aplicável.

500:
erro sanitizado.

Utilizar Problem Details.

Preservar Request ID.
