# TASK-6.3 — BACKEND DE PLANEJADO VERSUS REALIZADO

PROJETO: EQUILIBRA
SPRINT: 6 — PLANEJAMENTO FINANCEIRO
STACK: Spring Boot 4 + MySQL + Angular 19

CONTEXTO

Sprint 5 aprovada.
TASK-6.0 — Arquitetura do Planejamento Financeiro concluída.
TASK-6.1 — Backend de Orçamentos por Categoria concluído.
TASK-6.2 — Interface de Gestão de Orçamentos concluída.

OBJETIVO

Implementar o backend responsável pelo acompanhamento
mensal de orçamentos por categoria, calculando:

- valor planejado;
- valor realizado;
- valor restante;
- percentual de consumo;
- totais consolidados;
- informações necessárias para indicadores e gráficos.

O valor realizado deve derivar das despesas reais,
respeitando o ledger e as regras aprovadas.

NÃO implementar frontend nesta TASK.

O ADR da TASK-6.0 e os contratos reais prevalecem
sobre exemplos deste prompt.

==================================================
3. FONTE DE VERDADE
==================================================

O valor realizado deve ser calculado a partir
das despesas efetivamente válidas.

Não utilizar:

- saldos de contas;
- patrimônio líquido;
- receitas;
- transferências;
- valores preenchidos pelo frontend;
- totais materializados sem justificativa.

Não persistir actualAmount como campo mutável
do orçamento, salvo decisão explícita do ADR.

==================================================
4. COMPETÊNCIA MENSAL
==================================================

Usar a competência aprovada no ADR.

Exemplo:

2026-10.

Converter para o intervalo temporal correto,
considerando a política real de timezone.

Preferir intervalo semiaberto:

[início do mês, início do mês seguinte)

quando consistente com a arquitetura existente.

O campo financeiro de referência é occurredAt.

Não utilizar createdAt para determinar o mês
de consumo do orçamento.

==================================================
5. DESPESAS VÁLIDAS
==================================================

Somar apenas despesas que:

- pertencem ao usuário autenticado;
- possuem status financeiro válido/ACTIVE;
- estão na competência consultada;
- pertencem à categoria do orçamento;
- satisfazem os demais critérios aprovados.

Usar magnitude positiva de despesa.

Não inverter sinais incorretamente.

==================================================
6. DESPESAS CANCELADAS
==================================================

Despesas canceladas não devem contribuir
para actualAmount.

Se uma despesa for cancelada após ter sido
contabilizada anteriormente, a próxima consulta
deve refletir automaticamente a exclusão.

Não criar rotina de sincronização manual.

==================================================
7. RECEITAS
==================================================

Receitas não consomem orçamento de despesas.

Categoria BOTH:

somente transações EXPENSE devem entrar
no cálculo de actualAmount.

Não compensar gastos com receitas da mesma categoria.

==================================================
8. TRANSFERÊNCIAS
==================================================

Transferências não consomem orçamento.

Não incluir movimentos de transferência
na soma de despesas.

Transferências entre contas próprias não representam
consumo de orçamento de categoria.

==================================================
9. CATEGORIAS INATIVAS
==================================================

Um orçamento histórico associado a categoria
posteriormente desativada deve permanecer consultável
conforme ADR.

As despesas históricas válidas continuam contribuindo
para o realizado.

Não filtrar automaticamente category.active=true
nas agregações históricas.

==================================================
10. DESPESAS SEM CATEGORIA
==================================================

Inspecionar se Expense sem categoria é permitida.

Aplicar a política aprovada no ADR.

Não criar automaticamente uma categoria
"Sem categoria" no banco.

Se despesas sem categoria não pertencem a nenhum
orçamento, mantê-las fora do total realizado
dos orçamentos definidos.

Documentar eventual indicador separado de
despesas não orçadas, se aprovado.

==================================================
11. CONTAS FINANCEIRAS
==================================================

O orçamento por categoria deve seguir o escopo
de contas aprovado no ADR.

Se orçamento for global por categoria:

somar despesas de todas as contas próprias.

Não aplicar filtros de conta não previstos.

Não duplicar despesas devido a joins com
movimentos de conta, tags ou anexos.

==================================================
12. FÓRMULAS
==================================================

Para cada orçamento:

plannedAmount = valor cadastrado.

actualAmount = soma das despesas elegíveis.

remainingAmount = plannedAmount - actualAmount.

consumptionPercentage =
(actualAmount / plannedAmount) * 100.

Usar BigDecimal.

Definir escala e arredondamento conforme ADR.

Não usar float/double.

Não truncar consumo acima de 100%.

==================================================
13. ORÇAMENTO ZERO
==================================================

Se plannedAmount=0 for permitido pelo ADR,
definir semântica exata para:

actualAmount=0;
actualAmount>0;
remainingAmount;
consumptionPercentage;
status derivado.

Nunca dividir por zero.

Não inventar percentual infinito.

Se zero for proibido, cobrir a restrição
nos testes e contratos.

==================================================
14. VALORES ACIMA DO LIMITE
==================================================

Exemplo:

plannedAmount=1000.00
actualAmount=1150.00

Esperado:

remainingAmount=-150.00
consumptionPercentage=115.00

Não limitar percentual a 100%.

Não transformar saldo negativo em zero.

implementá-los conforme contrato.

Exemplos conceituais:

sem consultar o ADR.

Se a lógica de alertas foi reservada para TASK-6.5,

de alertas nesta TASK.

Não expor ownerId desnecessariamente.

==================================================
18. TOTAIS CONSOLIDADOS
==================================================

Para os orçamentos definidos na competência:

totalPlanned = soma dos plannedAmount.

totalActual = soma do realizado de cada orçamento.

totalRemaining = totalPlanned - totalActual.

Definir totalConsumptionPercentage conforme ADR.

Não calcular média simples dos percentuais
das categorias, pois isso distorce o consolidado.

Se permitido:

totalConsumptionPercentage =
totalActual / totalPlanned * 100.

Tratar totalPlanned=0 explicitamente.

==================================================
19. DESPESAS NÃO ORÇADAS
==================================================

Definir e respeitar o escopo aprovado:

Despesas em categorias sem orçamento não devem
ser adicionadas artificialmente ao realizado
dos orçamentos cadastrados.

Se houver campo unbudgetedExpenses,
calcular de forma separada e explícita.

Não misturar:

totalActual de orçamentos definidos

com

totalExpense do mês inteiro.

==================================================
20. ORÇAMENTO SEM DESPESAS

remainingAmount=500.00
consumptionPercentage=0, se definido pelo ADR.

O orçamento deve aparecer mesmo sem movimentos.

23. CONSULTAS SQL
==================================================

Executar agregações no MySQL.

para somá-las no Java.

Usar consultas owner-scoped.

Garantir que cada despesa seja contabilizada uma vez.

Preferir consultas agrupadas por categoria
para todos os orçamentos da competência.

==================================================
24. N+1
==================================================

Não executar uma consulta de despesas
para cada orçamento.

Evitar:

for (budget : budgets) {
  repository.sumExpenses(budget.categoryId);
}

Preferir agregação em lote.

Verificar quantidade de queries conforme
instrumentação disponível.
